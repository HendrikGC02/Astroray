# pkg259 Phase 0 — Cycles feature-coverage reference-corpus design

**Status:** Phase 0 design only. No `.blend` scenes exist yet; nothing here
is built, rendered, or gated. This document is the deliverable of Phase 0
(spec: `.astroray_plan/packages/pkg259-cycles-feature-coverage-reference-scenes.md`).
It is the input to Phase 1 (`materials_hall` + `textures_mapping` builders).

**Author:** Claude (lead session), 2026-09-08. Astra (`gpt-6-astra` via Codex
CLI) contributed one read-only brainstorm pass — see §5.

---

## 0. Why this document exists

Astroray currently measures its own Blender/Cycles feature coverage with an
AST-scanned matrix (`docs/blender_parity/coverage_matrix.json`, 527 rows:
114 SUPPORTED / 50 APPROXIMATED / 363 DROPPED-SILENT) but has no systematic
way to *exercise* that coverage in a rendered scene — every existing
benchmark scene (`metal_sweep`, the three #729 parity scenes, the pkg119b
single-sphere debug library, `benchmarks/showcase` presets) was picked ad
hoc for its own purpose, not to guarantee coverage. This document designs a
seven-family corpus of deliberately attractive Blender scenes, each carrying
a manifest of the Cycles features it exercises, such that:

- every SUPPORTED/APPROXIMATED matrix row lives in >=1 scene (provable by a
  test, not eyeballing);
- every DROPPED-SILENT row is recorded as a "gap card" and, where cheap, is
  made visible in the rendered image itself;
- the three Pillar-4 exit-gate (c) scenes and gate (b)'s frequency-weighted
  coverage measurement both draw from this same corpus instead of one-off
  assets.

Phase 0 (this document) produces the design and the feature-to-scene
allocation. Phases 1-4 (separate sessions, per the spec's phasing) build the
`.blend` files, the harness integration, and the coverage report.

## 1. Scene families

Seven families, per the spec. Row counts below are generated by
`.astroray_plan/docs/pkg259-phase0/build_allocation_table.py` (§2) against
`docs/blender_parity/coverage_matrix.json` as of 2026-09-07 (post pkg253
scanner fix). "Rows" = distinct (category, feature, socket_or_prop) triples;
one Blender node/light/camera/render-setting can own several rows.

### 1.1 `materials_hall` — 166 rows (10 SUPPORTED / 38 APPROXIMATED / 118 DROPPED-SILENT)

**Concept.** Every BSDF/closure Cycles ships, staged as one continuous
gallery corridor rather than a flat grid of spheres on grey (the owner's
explicit complaint about the old material contact sheet). One alcove per
closure family; consistent studio three-point + one warm practical light so
BSDF differences read clearly against a fixed lighting reference (the Cycles
`tests/render/` convention: isolate the variable). Glass objects are lifted
slightly off their pedestals per the composition rule (never flush on a
plane); everything is shade-smooth.

**Composition/camera.** One wide dolly-down-the-corridor shot for the
README hero image (zoom onto the alcove that reads best, per "zoom the
camera onto the important part"); the coverage report reuses per-alcove
crops from the same high-resolution establishing render rather than
rendering N separate frames (cheaper, and keeps every alcove under
identical lighting for a fair comparison).

**Alcove inventory** (object -> features):

**Coverage-claim rule (adopted from Astra, §5 — applies to every alcove,
and to every family below):** a `feature_tags` entry is only valid if the
socket is *active* (a connected Coat Roughness with Coat Weight at zero
earns no coverage) and its effect is visible in a defined image region —
not merely wired. Alcove D's `Coat Normal` sub-socket therefore gets its
own isolated variant on an otherwise-smooth base surface, so its
contribution cannot be confused with the base normal map (Row 4,
`textures_mapping`).

**Absorbs:** `material_zoo` (#729 corpus, 8450 tri, Principled + checker +
normal-map) folds into Alcove D as the "everyday materials" reference (its
Principled/checker/normal-map content is cross-tagged, not rebuilt);
`blender_addon/scenes/metal_sweep.blend` folds into Alcove B; the pkg119b
single-sphere-per-feature library is retired — its per-feature
`scene_library.build_shader_node_scene` builders become the per-alcove
content, called from `build_corpus.py` instead of standalone debug scripts.

**Expected cost.** Heaviest family by row count and by noise (Glossy/SSS/
hair need real samples to look clean). CPU reference at 512x384, 256-512
spp; budget ~5-10 min per full-corridor CPU render.

### 1.2 `textures_mapping` — 221 rows (69 SUPPORTED / 0 APPROXIMATED / 152 DROPPED-SILENT)

**Concept — revised after the Astra brainstorm (§5).** The largest family
by row count, and the one place Astra's critique changed the plan
outright: a flat "sample wall" of tile cards is exactly the old
material-contact-sheet shape the owner already called "flat and boring."
Adopted instead: a **printmaker's/textile workshop** — a large patterned
fabric draped from a printing table with folds, seams, and an overhanging
edge (continuity across a fold/seam is itself a mapping-correctness tell:
a dropped UV or transform breaks registration, reverses a motif, or
changes its scale where the fabric bends), curved printing rollers,
stacked ceramic reliefs, and hanging paper proofs, under raking light for
surface-detail depth. The fabric is the README hero shot; the proofs and
reliefs carry the rigorous per-node coverage as **close crops with small,
independent node graphs**, not one shared complex material (avoiding
chained-node errors that could visually cancel each other out). Node-graph
outputs still feed Emission (not a BSDF) on the diagnostic proofs so
texture legibility is never confounded by materials_hall's BSDF fidelity —
kept from the original plan.

Natural homes for the procedural families: Wave and Checker on woven
fabric; Noise and Voronoi on glazed reliefs; Brick on a miniature
architectural panel; Gradient on a print; Magic and Gabor on decorative
proofs; White Noise on a stippled ink sample. Converter-node diagnostics
(Math/Vector Math with inputs chosen to distinguish the operation, Map
Range/Clamp with values crossing their bounds, Mix with unequal inputs and
an intermediate factor, Curves/ColorRamp with visibly non-linear shapes,
Combine/Separate with unequal channels so a channel swap cannot vanish into
grey) live as small independent proofs near the fabric, not baked into it.

**Composition/camera.** Wide shot of the workshop for the README hero;
tight crops on the proofs/reliefs for the coverage report (same reuse
pattern as `materials_hall` — one high-resolution establishing render,
cropped per feature, not N separate renders).

**Row inventory** (still organized in five sub-groups for the allocation
table below; physically these are workshop proofs/reliefs/fabric regions
per the revised concept above, not a literal grid of tiles):

### 1.3 `lighting_studio` — 35 rows (24 SUPPORTED / 0 APPROXIMATED / 11 DROPPED-SILENT)

**Concept.** A photography-studio still life (a metal sphere, a matte cube,
a fabric-draped object, a small prism) shot four ways — one per light type
— composited as a 2x2 contact sheet (a direct callback to the AOV-stack
layout the owner explicitly liked). A curved reflective surface, a matte
wall, and a narrow upright object casting a shadow sit in every quadrant so
source shape, illumination footprint, and penumbra are all legible
together (Astra, §5). One Spot/Point fixture carries a real IES
photometric profile.

**Correction (Astra, §5):** an IES file encodes *directional intensity*,
not an arbitrary projected image — "gobo pattern" was the wrong mental
model in the original plan. The fixture should use an asymmetric
wall-washer or a pronounced multi-lobed photometric profile, positioned so
the lobes are visibly distinct on the backdrop; a dropped `TEX_IES` then
shows as a plain uniform cone next to its three siblings, which is still an
excellent, visible tell — just for the right reason.

Diagnostic images in this family are **not** exposure-normalized to equal
brightness — doing so would conceal power, temperature, or spread errors
(Astra, §5).

**Composition/camera.** Fixed camera and still-life across all four
quadrants so the only variable is the light rig — the direct visual
comparison is the point.

**Inventory:** POINT (energy/colour/temperature/soft_size), SUN
(angle-driven soft shadows), SPOT (cone/blend/show_cone), AREA
(shape/size/size_y/spread), `ShaderNodeTexIES` (photometric profile),
`OUTPUT_LIGHT` (light-group node — *assignment* lives here; the rendered
light-group *pass* is a `render_settings` concern, §1.7).

**Not matrix-tracked, noted for completeness (Astra, §5):** Blender's
per-object light-linking/shadow-linking collections (a coloured accent
lighting one nominated object while an adjacent receiver stays unaffected,
plus a separate shadow-linking blocker test) are real Cycles 4.x+ features
with no row in `coverage_matrix.json` at all — the scanner does not
enumerate them. Not added to this family's required scope in Phase 0 (see
open question §7.6).

**Absorbs:** none of the #729 three directly (`cornell_interior` uses one
plain area light only) — new coverage.

**Expected cost.** Cheap geometry; area-light MIS can be noisy at low spp —
128-256 spp for clean soft shadows.

### 1.4 `world_sky` — 25 rows (1 SUPPORTED / 0 APPROXIMATED / 24 DROPPED-SILENT)

**Concept.** An open-air "observation deck" exterior with one reflective/
refractive hero object (glass or chrome sphere — the composition the owner
already loved in the existing HDRI/3-sphere showcase render, unchanged),
shown twice: once under a working HDRI environment (Poly Haven exterior,
golden-hour) and once under the currently-unsupported Sky texture (sun-disc
+ turbidity), so the drop is literally a black sky next to its working HDRI
twin — the spec's explicit "visible drop" example. A small strip of inset
thumbnails demonstrates world rotation/strength.

**"Three independent opportunities to prove itself" (adopted from Astra,
§5)** — a world-lighting scene that only shows a correct background is not
sufficient evidence: the environment must independently (1) show the
background directly, (2) show correct reflected environment structure on
the hero object, and (3) illuminate a shaded recess or crevice with
indirect environment light. This catches the specific failure mode where
the HDRI displays correctly *behind* the scene but contributes nothing (or
wrongly) to lighting. An asymmetric bright landmark in the environment
makes world rotation legible in both background and reflection at once; a
slender post and its cast shadow give a visual "compass" for sun direction.

**Black sky is not the only failure signature (Astra, §5):** a dropped Sky
parameter may leave a *plausible-looking* default sky instead of a black
one. Pair a low/high-haze or different-sun-position variant to expose a
control that is silently ignored rather than assuming absence alone proves
the drop.

**Sky-model inventory pinned to the build (Astra, §5):** Blender 5.2's Sky
Texture node documents Multiple Scattering plus Nishita-derived Single
Scattering, with Hosek/Wilkie retained as a legacy option — the corpus
should enumerate `sky_type` against the actual pinned Blender version at
build time, not treat "14 props" as permanently fixed.

**Composition/camera.** Same hero framing for both halves so the HDRI-vs-
Sky comparison is a true A/B, not a different composition; HDRI and Sky
variants are compared each against its *own* Cycles reference, never
against each other (two different lighting models should not be expected
to match).

**Inventory:** TEX_SKY (14 props: sky_type, sun_*, turbidity, ozone/
aerosol/air density, ground_albedo), TEX_ENVIRONMENT (HDRI loader,
cross-tagged materials_hall for reflection use), BACKGROUND (world shader),
OUTPUT_WORLD, `World.use_nodes`.

**Absorbs:** the HDRI half of `hdri_exterior_hair` (#729) — its reflective/
refractive object and environment texture usage fold in here; its hair
content moves to `geometry_zoo` (§1.5). Whether this is one shared `.blend`
feeding two manifest entries or two files sharing an asset is a Phase-1
decision (§6), not resolved here.

**Expected cost/risk.** HDRI convergence depends on environment importance
sampling, which is not yet wired end-to-end (memory `env-nee-absent-cdf-
sampler-unused`; pkg258 owns landing it). Until pkg258 lands, the HDRI half
of this scene may render noisier than its Cycles reference at matched spp —
**flagged as a cross-package dependency risk**, not something Phase 1 fixes.

### 1.5 `geometry_zoo` — 35 matrix rows here are volume-shader nodes only (0 SUPPORTED / 12 APPROXIMATED / 23 DROPPED-SILENT); see §1.5 note on the matrix gap

**Concept.** A "cabinet of curiosities," split into two frames per Astra's
critique (§5) that a single combined turntable makes the harder features
too small to read:

- **Solid cabinet:** an instanced arc of repeated mineral casts (geometry
  instancing — distinct rotations/scales, including one mirrored transform
  and one material variation, not just N identical copies), a fur-lined
  case (hair/fur patch, reusing the #729 `_build_hair_curves` builder,
  shown against a contrasting backing plus a sparse-strand crop revealing
  thickness/taper/missing-curve issues), a chamfered mechanical specimen
  with both broad flat faces and curved transitions carrying a
  smooth-vs-flat-vs-auto-smooth trio (sharper than a plain sphere at
  telling the three modes apart; callback to memory
  `cycles-caustics-need-smooth-shading`), a live-modifier-stack-vs-baked
  comparison (the two must match) **plus an explicit third undeformed-base
  state** (Astra: "applied vs not applied" alone is ambiguous about what
  "not applied" means), and a rigid spinning vane (rigid motion blur) next
  to a flexible ribbon (deformation blur) — both single-frame, sub-frame
  motion per the spec's no-animation-sequences non-goal.
- **Volume cabinet:** open specimen frames holding the volume bounds
  directly (no glass shell, which would confound refraction with the
  volume itself), backlit with repeated bars/a striped plaque so
  absorption (reduced transmission with thickness), scattering (softened/
  obscured background), and emission (visible in a lights-off variant) are
  each independently legible; illumination direction varies across
  specimens so Volume Scatter's anisotropy parameter actually matters, and
  at least one specimen uses a spatially-varying density for a recognizable
  internal structure.

**Composition/camera.** Radial "lazy susan" layout per cabinet, single
static frame each, camera at a 3/4 elevated angle so every curio is legible
without a full 360 turntable render sequence (spec forbids animation
sequences).

**Inventory (matrix-tracked):** PRINCIPLED_VOLUME, VOLUME_SCATTER,
VOLUME_ABSORPTION, VOLUME_COEFFICIENTS.

**Known matrix gap (flagged, not fixed here):** instancing, hair-as-
geometry-object, modifier stacks, motion blur, and smooth/flat/auto-smooth
shading are real Cycles features this family is supposed to cover per the
spec's own "Files to create" row, but `coverage_matrix.json` has no
scene-graph/object category at all — only `shader_node`, `light`,
`render_settings`, `camera`, `world`. The Phase-A scanner
(`scripts/generate_blender_parity_matrix.py`) enumerates shader-node
sockets and a few datablock categories, not `Object`/`Mesh`/`Modifier`
properties. This means `geometry_zoo`'s non-volume content cannot be proven
covered by `tests/test_reference_corpus_manifest.py`'s matrix-join check —
it can only be visually verified. **Open question for the owner (§7).**

**Absorbs:** the hair/curve object from `hdri_exterior_hair` (#729) moves
here (non-HDRI half).

**Expected cost.** Hair and volume are the most expensive elements
(curve intersection, volume marching) — keep counts small; this is a
coverage scene, not a stress benchmark (pkg241 keeps its own separate
stress scenes, untouched by this package).

### 1.6 `camera_lens` — 12 rows (6 SUPPORTED / 0 APPROXIMATED / 6 DROPPED-SILENT)

**Concept.** One room, one tripod mark, four camera rigs, 2x2 grid (same
layout pattern as `lighting_studio`, deliberately — a recognizable
"comparison contact sheet" visual language across the corpus): (a)
shallow-DoF portrait of `materials_hall`'s Principled bust with an
aperture-blades bokeh-shape test, (b) orthographic architectural elevation
of the corridor, (c) panoramic/fisheye establishing shot of the whole hall,
(d) a near/far clip demonstration.

**Inventory:** lens, sensor_width/height, shift_x/y, aperture_fstop,
aperture_blades, aperture_rotation, aperture_ratio, camera type
(perspective/orthographic/panoramic), clip_start, clip_end.

**Not matrix-tracked, noted for completeness (Astra, §5):** focus distance
(DoF distance vs. focus object), orthographic scale, sensor fit, and
render aspect ratio are all real Cycles camera parameters with no row in
`coverage_matrix.json`'s 12-row `camera` category — another scanner gap
alongside `geometry_zoo`'s (§1.5) and §7's Geometry/Object Info/Light Path
nodes. The bokeh-shape tell (polygonal vs. circular aperture blades,
followed by a rotation change, rather than one pleasing blur) is the
family's strongest single visible-drop device.

**Absorbs:** none directly — reuses `materials_hall` geometry so no new
scene content, only camera variation.

**Expected cost.** Cheapest visually-rich family; DoF quality needs modest
spp (128) to avoid a noisy bokeh disk misreading as a shape bug.

### 1.7 `render_settings` — 33 rows (4 SUPPORTED / 0 APPROXIMATED / 29 DROPPED-SILENT)

**Concept.** Not a geometric scene — a settings matrix over one fixed hero
shot (reuse `lighting_studio`'s still life at a resolution where fine
metal edges, glass, cloth and shadow detail survive downscaling — Astra's
refinement, §5), rendered as a **six-panel pass sheet**: beauty, depth,
normals, a custom AOV, a Cryptomatte selection (demonstrated through an
actual object pick, not a raw colourful ID buffer), and a sample-count
panel — this directly answers the owner's explicit ask ("more passes, e.g.
depth and number-of-samples heatmaps") without cramming everything into one
unreadable dashboard. A **second** presentation covers denoise and
convergence separately: a samples-convergence strip using an **independent,
higher-spp reference outside the plotted series** (owner note: the old
convergence graph used its own last sample as the reference, producing an
implausibly smooth curve) and a denoise before/after pair (owner note: the
old one was praised but low-res and on a boring scene — this reuses the
corpus's own hero shot instead).

Additional variants: a film-transparent alpha checkerboard; a **removable
bounce-limit diagnostic rig** around the hero subject (opposed mirrors for
reflection-depth, stacked transparent sheets for transmission-depth, a
diffuse recess for indirect-bounce depth, the geometry_zoo volume frame for
volume-bounce depth) with all *other* depth limits set high enough that only
the tested limit controls the result — a plain bounce-count slider alone
does not prove which bounce type it is gating; a blank/black `OUTPUT_AOV`
pass shown next to the working depth pass, with a distinctive AOV motif
written by a matching Cycles render so the comparison shows *what the
missing AOV should contain*, not just that it is missing; and a light-group
panel (key/fill contribution reconstructed separately), since light-group
*assignment* lives in `lighting_studio` (§1.3) but *pass delivery* is a
render-settings concern (Astra's ownership split, §5).

**Adaptive sampling is not a visual contact-sheet item** (correction from
Astra, §5): a correctly implemented adaptive sampler need not change a
*converged* beauty image at all — the real evidence is the actual
per-pixel sample count distribution (a heatmap) and noise at matched
*total* sample budget, not an on/off appearance diff. The sample-count
panel above is therefore the adaptive-sampling test, not a separate
before/after pair.

**Inventory:** `RenderSettings` (17 props: samples, adaptive sampling x3,
seed, sample_offset, film_exposure, film_transparent, filter_width,
per-bounce-type depths x6, caustics x2, use_fast_gi, use_denoising,
denoiser, denoising_input_passes), OUTPUT_AOV, OUTPUT_LINESTYLE +
UVALONGSTROKE (Freestyle line-rendering — one integration case, not a
texturing node; moved here from `textures_mapping` per §5).

**Absorbs:** the weekly-bench's `cornell`/`textured_plane` render-settings
usage folds in here per the spec's file-to-modify list
(`weekly_local_bench.ps1`).

**Expected cost.** Cheapest to build (re-renders of one scene per flag),
but many renders — one per setting variant; batch-render friendly, and the
first family that can run unattended overnight if the fixed hero shot is
already built.

## 4. Manifest schema proposal and tool interfaces (design only)

### 4.1 Manifest schema (extends #729's `manifest.json`)

The #729 schema (`benchmarks/blender_parity/scenes/manifest.json`) already
has: `blend_path`, `sha256`, `settings` (res/spp/engine), `reopen_verified`,
`triangle_count`, `curve_count`/`curve_point_count`, `object_counts`,
`node_ids`, and a per-engine `{ok, non_vacuity, png}` block. Proposed
additions per scene entry:

```jsonc
{
  "family": "materials_hall",              // one of the 7 family names
  "builder_fn": "build_materials_hall_scene",  // scene_library.py function, for traceability
  "feature_tags": [                        // subset of coverage_matrix.json rows this scene covers
    {"category": "shader_node", "feature": "BSDF_GLASS",
     "bl_idname": "ShaderNodeBsdfGlass", "socket_or_prop": "input:IOR",
     "classification": "SUPPORTED", "gap_card": false}
    // ... one entry per (category, feature, socket_or_prop) exercised,
    // shape mirrors coverage_matrix.json rows exactly so coverage_report.py
    // can join on the same tuple key without a translation layer
  ],
  "assets": [                              // every non-procedural asset used
    {"path": "benchmarks/reference_corpus/assets/golden_hour.hdr",
     "sha256": "...", "license": "CC0 1.0", "source_url": "https://polyhaven.com/a/..."}
  ]
  // node_ids, sha256, object_counts, non_vacuity, reopen_verified: unchanged shape from #729
}
```

`feature_tags` entries with `"gap_card": true` mark a DROPPED-SILENT
feature the scene deliberately includes for visibility (e.g. the Sky-
texture black-sky tile in `world_sky`) — this is how
`tests/test_reference_corpus_manifest.py` distinguishes "this DROPPED-
SILENT feature has a documented, intentional gap card in this scene" from
"this scene author forgot to tag it."

**Coverage-claim rule (adopted from the Astra brainstorm, §5.1) — governs
what a builder is allowed to write into `feature_tags`:** a socket/prop may
only be tagged if (1) it is connected/active in the node graph — a wired
but functionally inert input (e.g. Coat Roughness with Coat Weight at 0)
does not count — and (2) its effect falls within a documented image region
of that scene (a crop rectangle or a named object), so `coverage_report.py`
and a human reviewer can both point at *where* the feature's contribution
is visible. This is stricter than "the node exists in `node_ids`" (which
`test_family_declared_features_present_in_scene`, §4.4, still checks
separately) — it is a claim about demonstrated effect, not mere presence.

### 4.2 `build_corpus.py` (design only — no code written in Phase 0)

```python
def build_corpus(bpy, out_dir: Path, families: list[str] | None = None) -> dict:
    """Orchestrator. For each requested family (default: all seven), call
    the matching scene_library.py builder(s), save .blend, collect a
    manifest entry per §4.1, write scenes/manifest.json. Returns the
    manifest dict (also used by tests without re-reading the file)."""
```

Per **Key design decision** ("deterministic builders over hand-authored
files") and CLAUDE.md §5b (no duplicate scene-construction modules), the
new per-family builder functions (`build_materials_hall_scene`,
`build_textures_mapping_scene`, etc.) are added to
`benchmarks/blender_parity/scene_library.py` — which already is the
project's "generic node-wiring + composite scenes" module and owns
`REFERENCE_SCENES` — rather than creating a second parallel scene-
construction module under `benchmarks/reference_corpus/`. `build_corpus.py`
itself stays a thin CLI wrapper: argument parsing, calling into
`scene_library.py`, and writing the manifest — mirroring how
`harness.py --export-blend` already drives `scene_library.py` today.

### 4.3 `coverage_report.py` (design only)

```python
def load_manifests(corpus_dir: Path) -> dict[str, dict]: ...
def join_matrix(matrix_rows: list[dict], manifests: dict) -> tuple[
    dict[tuple, list[str]],   # covered: (category, feature, bl_idname, socket_or_prop) -> [scene names]

def render_verdicts(triage_report: dict) -> dict[tuple, str]:

    reads, it does not compute a new metric (spec non-goal: no new
    comparison metric stack)."""
def write_report(covered, uncovered, verdicts, out_md: Path, out_json: Path) -> None: ...
```

Output: `docs/blender_parity/corpus_coverage.md` + a machine-readable JSON
twin, matching the spec's "Files to create" row.

### 4.4 `tests/test_reference_corpus_manifest.py` (design only)

Proposed test functions (extends the pattern in the existing
`tests/test_reference_scene_corpus.py`, which only covers the three #729
scenes):

- `test_every_blend_reopens_and_sha_matches` — parametrized over every
  corpus scene (not just three), same reopen+hash check as today.
- `test_manifest_node_ids_match_file` — reopen headless, diff the
  `bl_idname` set actually present in the file against the manifest's

- `test_family_declared_features_present_in_scene` — per scene, every

## 5. Astra brainstorm record

Per the spec's "Phase 0 brainstorm with Astra" design decision and the
owner's request, one read-only Codex session
(`codex exec -m gpt-6-astra -s read-only`) was run against a prompt
(`.astroray_plan/docs/pkg259-phase0/astra_prompt.md`) containing the
north-star excerpt, the full family list with row counts, the owner's
composition rules, and four explicit asks: creative scene concepts,
overlooked features, ways to make silent drops visible, and a critique of
the allocation. **Outcome: the call succeeded** (exit 0, no CLI error), one
call as budgeted, no retry, no other model used. Full transcript:
`.astroray_plan/docs/pkg259-phase0/astra_response.md` (4698 lines including
the CLI's own tool-use/reasoning log; the substantive reply is the last
~200 lines). 81,796 tokens used for the call.

### 5.1 Astra's core framing (accepted in full)

Astra proposed a stricter **coverage-claim rule**, adopted verbatim into
§4.1's manifest design and cross-referenced from every family section: *"a
`feature_tags` entry is only valid if the socket is active, its effect is
conditionally necessary (a connected Coat Roughness with Coat Weight at
zero earns no coverage), and its effect falls in a defined, visible image
region."* This is a genuine rigor gap the original draft did not have — the
original plan would have let a scene claim coverage for a socket that was
merely *wired*, not *provably effective*. It is now the operative
definition of "covered" throughout this document.

Astra's guiding distinction — "this feature appears somewhere in the scene"
vs. "this image would visibly change if the feature stopped working" — is
the same idea in different words, and both are now stated in §0/§4.1.

### 5.2 Accepted and folded into the relevant family section

- **materials_hall (§1.1):** Ray Portal built as an "impossible doorway"
  to a differently-lit, differently-coloured destination room, tested at a
  non-default position/rotation, not a same-room mirror; Add/Mix Shader
  stack uses visibly different branch inputs and a non-trivial intermediate
  factor (two identical branches can hide a broken translation); Holdout
  gets an explicit RGB-vs-alpha comparison, not a beauty render alone;
  Coat Normal gets its own isolated variant separate from the base normal
  map; Blackbody/Wavelength reframed as Cycles colour-producing converter
  nodes (not a claim about physical spectral dispersion) — corrected a
  genuine overclaim in the original draft, which had implied the Wavelength
  alcove would demonstrate real spectral rendering.
- **textures_mapping (§1.2):** the tile-wall concept replaced outright with
  a printmaker's/textile workshop (fabric folds/seams as a mapping-
  correctness tell, small independent proofs instead of one shared complex
  material to avoid error-cancelling chains) — the one place Astra's
  critique changed the plan rather than refined it, because it directly
  targets the owner's named "flat and boring" complaint about the
  predecessor material contact sheet.
- **lighting_studio (§1.3):** corrected a real factual error — IES stores
  directional intensity, not a projected "gobo" image; fixed the fixture
  choice (asymmetric wall-washer / multi-lobed profile) and the framing
  language accordingly. Added: no exposure-normalization across the four
  light-type quadrants (would hide power/temperature/spread errors); a
  curved reflective surface + matte wall + upright shadow-caster in every
  quadrant so source shape, footprint, and penumbra are all legible
  together.
- **world_sky (§1.4):** the "three independent opportunities" rule
  (background, reflection, indirect illumination of a shaded recess) closes
  a real gap — the original plan would have accepted "the background looks
  right" as sufficient evidence, which cannot catch a world that displays
  but does not illuminate. Added: black sky is not the only failure
  signature (a dropped param may leave a plausible default); pin the
  sky-model inventory to the actual Blender 5.2 docs rather than treating
  "14 props" as permanent; HDRI and Sky variants each compare only to their
  own Cycles reference, never to each other.
- **geometry_zoo (§1.5):** split into a solid cabinet and a volume cabinet
  (one combined turntable was correctly judged too crowded to read);
  "modifier applied vs not applied" expanded to three explicit states
  (live stack / baked / undeformed base) since the original two-state
  framing was ambiguous about what "not applied" meant; volume specimens
  moved into open frames (no glass shell, which would have confounded
  refraction with the volume itself) with illumination direction varied so
  Volume Scatter's anisotropy parameter is actually exercised, not just
  wired.
- **camera_lens (§1.6):** the bokeh tell sharpened to a *pair* (polygonal
  vs. circular aperture, then a rotation change) rather than one pleasing
  blur, which proves very little about aperture controls on its own.
- **render_settings (§1.7):** expanded from an AOV-strip to a six-panel
  pass sheet (beauty/depth/normal/AOV/Cryptomatte/sample-count); light-group
  *pass delivery* placed here (assignment stays in lighting_studio); a
  removable bounce-limit diagnostic rig (opposed mirrors, stacked
  transparent sheets, a diffuse recess, the volume frame) with all other
  depth limits set high so only the tested limit controls the result; and
  a real correction — **adaptive sampling is not a visual before/after
  item**, since a correctly implemented adaptive sampler need not change a
  *converged* image at all; the real evidence is the per-pixel sample-count
  distribution, which the sample-count panel already provides. This
  replaced an inaccurate design in the original draft.
- **Cross-family regrouping:** `UVALONGSTROKE` moved from
  `textures_mapping` to `render_settings` to sit with `OUTPUT_LINESTYLE`
  (Freestyle is "a separate line-rendering/output integration case, not
  another material closure") — applied in the allocation script (§2) and
  reflected in the totals table.

### 5.3 Corroborated an existing finding

Astra independently flagged the same coverage-matrix scanner gap this
document had already identified in §1.5 — no scene-graph/object category
exists for instancing, modifiers, motion blur, or smooth-shading — and
extended it with a longer list this document had not found: Image Texture
sub-properties (Non-Color vs Color data, alpha, interpolation, extension,
projection, UDIMs), shader input nodes with no matrix row at all (Geometry,
Object Info, attribute/colour-attribute nodes, hair-info nodes, Light
Path), node-graph translation cases (nested groups, linked vs. constant
inputs), further Displacement sub-cases (midlevel/scale/space explicitly),
scene-export/visibility properties (camera/shadow visibility, negative
scale, custom normals, collection instances), and output/compositing
behaviour (alpha-over-background, shadow catcher, colour management). All
of this is **evidence the matrix itself under-enumerates Blender's feature
surface**, not something this package can fix (its job is to build scenes
against the matrix that exists) — folded into the open questions in §7
rather than the family sections, since none of it has a matrix row to
allocate against yet.

### 5.4 Rejected, and why

- **Full narrative reskin of every family** (museum conservation gallery,
  auction catalogue, expedition cabinet, clockmaker's workshop, coastal
  terrace) — genuinely appealing art direction, but adopted selectively
  rather than wholesale. Rewriting all seven concepts to a unified literary
  theme now would have meant discarding the object/composition specifics
  already drafted for no rigor gain in five of the seven families (only
  `textures_mapping`'s reskin directly fixes a named owner complaint, §5.2);
  the spec asks for "attractive," not for a themed anthology, and a
  builder implementing Phase 1 needs concrete object lists more than prose
  atmosphere. The *specific* tells and corrections embedded in each reskin
  (Ray Portal doorway, IES correction, three-opportunities world test,
  solid/volume split, six-panel pass sheet, etc.) were extracted and
  adopted individually instead — that is where the actual value was.
- **Light linking / shadow linking as required Phase 1 scope**
  (`lighting_studio`) — not in `coverage_matrix.json`'s 527 rows at all;
  adding it now would mean scoring coverage against features the matrix
  does not track, which breaks this document's own "generated, not
  hand-written" allocation discipline (§2). Logged as an open question
  (§7.6) for a possible scanner extension instead.
- **UDIM support for the `TEX_IMAGE` file-loading proof** — real, but
  disproportionate build/asset complexity for one row's `extension`
  sub-property; the existing (non-UDIM) extension/interpolation/projection
  sub-cases already have a matrix-tracked home and can be exercised without
  it. Logged as a possible Phase 1+ enhancement, not required.
- **Expanding `coverage_matrix.json` / `generate_blender_parity_matrix.py`
  in this package** to add the missing Geometry/Object Info/Light Path/
  camera-DoF-distance/ortho-scale/sensor-fit categories Astra (and this
  document, independently, for geometry_zoo) found — correct diagnosis,
  wrong package. `scripts/generate_blender_parity_matrix.py` belongs to
  pkg229/pkg119 Phase A, not pkg259; changing the scanner is out of this
  spec's authorized-files list. Logged as open questions (§7) instead of
  patched here.
- **"Do not manufacture a black or magenta failure appearance if the
  renderer produced something else"** — this is process guidance for
  Phase 1+ builders (be honest about what a drop actually looks like,
  don't over-dramatize it), not a scene-family decision; folded into §4.4's
  test design intent (`gap_card` entries record what actually rendered) but
  not given its own subsection.

### 5.5 Gate-protection caution (carried to §7, not resolved here)

Astra's closing point — that diagnostic variants sharing a family "must
not accidentally inflate frequency weights through repeated easy nodes" for
gate (b), and that gate (c)'s three pinned scenes should stay pinned until
an explicit replacement is accepted — restates and sharpens a risk this
document had not spelled out. Both are carried into §7 as open questions
for the owner rather than decided unilaterally here, since gate (b)/(c)'s
exact scoring and pinning are owner-ratified north-star decisions
(`north-star-and-integration-gate-2026-09-07.md` §2), not something a
design doc should silently redefine.
