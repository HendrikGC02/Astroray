Post-mortem — what worked / what stalled

✅ 1. The opencode pipeline is genuinely functional end-to-end

Config → Blender-MCP/agents/hooks plugin → Task Scheduler → opencode run → orchestrator decision engine → parallel dispatch of two implementers → open-weight models doing real C++/Python/data work. This is the first fully-unattended opencode run and the core machinery held up.

❌ 2. The implementer never opened a PR (the single biggest stall)

Both implementers produced the work but issued no gh pr create. The most likely cause: the package-implementer agent's "empirical build before declare done" gate — in a fresh worktree a full CUDA build + pytest (which needs the built .pyd + Blender) is heavy, and the subagent ran out of steps/time before reaching the PR step. Fix: give Python/data-only packages a lighter "run pytest, skip CUDA build" path, and make "open the PR" happen earlier in the implementer loop.

❌ 3. Synchronous dispatch degenerated the 10-min cadence

opencode's task tool is synchronous, so each dispatch tick waited on the implementer (holding the tick lock 30–60 min). The "10-minute cadence" collapsed to ~1 effective tick/hour, and the lock gaps blocked intermediate ticks. Fix: enable OPENCODE_EXPERIMENTAL_BACKGROUND_SUBAGENTS so implementers run in background and the tick returns immediately (the design already assumed this for the hardware gate).

⚠️ 4. Re-dispatch not recorded → duplicate work

The ledger's impl_dispatches stayed empty, so every tick re-listed pkg213/pkg214 as candidates and re-dispatched them, spending tokens on repeat work. Fix: the orchestrator skill's Step-2 dispatch must call record_action(…, "impl_dispatched") (or set impl_dispatches) when it spawns an implementer.

⚠️ 5. Closeout never ran

No 2026-08-21 standup was written and the ledger wasn't finalized — Step 3 (standup + ledger save + worktree GC) never completed, consistent with the ticks ending in a blocked implementer wait rather than a clean closeout.
