## Owner decision on pkg160 — and why the fix got better

The owner picked **fix the CPU**, not the GPU. Investigating the term to
implement that, I found it has **three independent defects**, not the one Step 0
identified:

1. **Wrong table** — the Step-0 finding: `GGXEnergyCompensationLUT` estimates
   `E` with 256 uniform-hemisphere samples, cannot resolve a narrow GGX lobe, so
   `E → 0` as roughness → 0 and `Fms` pins near its `1/π` ceiling.
2. **Missing cosine.** `AGENTS.md:87` states `Material::eval()` returns
   **brdf × NdotL**. `singleScatter = F*D*G / (4*NdotV + 0.001f)` correctly bakes
   the cosine in (the `NdotL` cancels against the Cook-Torrance denominator). But
   `multiScatter = albedo_ * (Fms * msWeight * 1.3f)` carries **no `NdotL` at
   all** — it violates the eval() contract outright.
3. **An invented weight.** `msWeight = roughness*(2-roughness)` and the `* 1.3f`
   appear in no published formulation. That is a hand-tuned fudge factor, which
   CLAUDE.md §6 forbids.

**The fix is therefore not "repair the LUT" but "delete its role".** `metal.cpp`
is the *only* consumer of `GGXEnergyCompensationLUT` / `ggxMultiScatterCompensation`
(verified by grep), and the repo **already contains the correct implementation**
in the Disney path — `disney.cpp:96 ggxCompensationFactor`, which reads the
shipped Cycles-derived tables, is applied **multiplicatively** to the
single-scatter result at `disney.cpp:652`, and is cited to Kulla & Conty 2017 /
Cycles `microfacet_ggx_preserve_energy` (BSD-3-Clause). Its exact GPU twin
`gpu_ggxCompensationFactor` already exists and is already used at
`gpu_materials.h:904`.

Applying that same pattern to plain `metal` fixes all three defects at once — the
correct tables, the cosine inherited free because the multiplicand already
carries it, and no invented weight — and makes CPU/GPU parity **structural**
rather than something to keep chasing. It is also pure borrowing, no derivation.

Dispatched as a pkg160 rework on PR #527. Note there is a **third** copy of the
broken helper at `src/gpu/wavefront/stage_shade_metal.cu:114` that must be
reconciled, not left as a variant.

**Expect renders to change:** every rough metal gets *dimmer on the CPU*. That is
the intended consequence of the decision. Gates keyed to CPU metal brightness may
move; they are to be reported, not silently re-blessed.

## PR #528 — the last phantom overload, and a sweep that corrected itself

`gpu_wavefront_state.h` declared `launchStageInit` with 6 parameters while the
definition takes 8. pkg157 removed three duplicates of this pattern but correctly
left this one, because fixing it needs the `= 0` default removed or relocated
(a defaulted parameter cannot precede non-defaulted ones) — behaviour-affecting,
and unverifiable without a build the implementer could not run.

Resolution: the default is simply removed. All 6 call sites pass `sample_index`
explicitly, so it was never used.

**Verified rather than assumed:** full Release+CUDA build succeeds, and the change
is measurably inert — same scene/seed against the pre-change binary gives
**identical image sums** (22315.917969 both), max difference 2.48e-07 relative to
peak, i.e. the wavefront's own atomic-ordering noise floor and ~40× inside the
1e-5 convention.

**A methodological note worth keeping.** I swept every `void launchStage*`
declaration against its definition. The first pass flagged **three** mismatches —
including one in pkg157's *already-merged* code. That was my own parser counting
commas **inside parameter comments**. After stripping comments, pkg157's fix is
clean and exactly one real mismatch remains:
`launchStageInit(IntegratorStateSoA&, …)` at `integrator_state_soa.h:124`, a
4-param Phase-A.1 overload with **no definition and no caller**. Dead scaffolding;
reported rather than deleted per CLAUDE.md §3. The lesson: a textual sweep over
C++ signatures is worthless unless it strips comments first, and I nearly filed a
false regression against merged code because of it.

## pkg155 — a hypothesis I formed, tested, and killed

The GPU is compute capability **12.0**; the build targets `75;86;89`, justified by
a `CMakeLists.txt:54` comment citing CUDA 12.6 — while **12.8 is installed**.
`cuobjdump --list-elf -all` confirms the module ships SASS for sm_75/86/89 plus
matching PTX and **nothing for sm_120**, so every kernel on this machine runs via
**driver JIT from compute_89 PTX**. All of that is true and verified.

The inference — that JIT was causing the 221-register blow-up behind the ~5× —
is **false**. Controlled test, identical source at `60306a9`, only
`CMAKE_CUDA_ARCHITECTURES` differing:

| scene | sm_89 (JIT) | +sm_120 (native AOT) | |
|---|---|---|---|
| cornell_diffuse | 97.84 ms/render | **175.62** | **1.80× SLOWER** |
| cornell_glass | 123.03 | **206.10** | 1.68× slower |
| `shade_bucketed` | 239.33 ms, 221 regs | **603.89 ms, 229 regs** | 2.52× slower |

CUDA 12.8's offline `ptxas` produces materially worse Blackwell code than the
driver's JIT. **`75;86;89` is not merely acceptable, it is optimal here.**

What it settles: **the 221-register problem is intrinsic to the kernel, not a
build artifact** (native AOT gives 229), so Phase 1's recovery direction stands
unchanged — per-material shade split, `__launch_bounds__`, live-state audit. And
a plausible-looking lever is now ruled out *with numbers*, before a package was
spent on it. Full write-up: `.astroray_plan/docs/pkg155-sm120-negative-result.md`.

**Two methodological corrections, both mine:**
1. **`-Xptxas -v` counts are worthless under `-rdc=true`** — they read 127 (sm_89)
   and 40 (sm_120) against real post-link values of 221 and 229. I flagged that
   caveat when I took the numbers and then let them drive a hypothesis anyway; a
   caveat is worth nothing until it changes behaviour. **This kills the
   "compile-only bisect"**: pkg155 Phase 2 needs the GPU at every point and cannot
   parallelise with HW verification. Protocol corrected by the architect
   (`6527d60`), which re-scoped the bisect to an opportunistic gap-filler
   (~1–1.5 GPU-hours across 2–3 nights) with HW gates for active PRs always
   outranking it.
2. **Do not conclude from a tool invocation the tool flagged as incomplete** — my
   first `cuobjdump --list-ptx` reported "no PTX at all"; its own output said to
   retry with `-all`.

Tested in a throwaway detached worktree so the CMakeLists edit never touched the
repo — build-file changes are owner-gated, and in the end there was nothing to
propose.

**Worth reinforcing rather than burying:** both protocol-level mistakes today —
the architect's compile-only premise and my JIT hypothesis — died the same way,
by a controlled measurement whose author then published it against themselves.
