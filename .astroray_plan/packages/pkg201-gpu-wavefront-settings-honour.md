## Goal

pkg200 proved the GPU wavefront F12 path honours only `maxDepth`, seed, `filmExposure`, the pkg157 clamps, and the pkg197 denoise pass — and **silently drops the rest of the plumbed steering-wheel controls**. Every dropped control is a lie in the steering wheel: the exporter reads the native prop, the setter stores it, and `src/gpu/` never looks at it. This package closes the specific gaps pkg200 enumerated (findings A–F + the `use_light_tree` known-gap), one honour-matrix row at a time.

**This package flips rows, it does not add settings.** Success for every item = the corresponding pkg200 row flips **HONEST-FAIL → PASS** when the pkg200 driver is re-run *verbatim*. The matrix is the gate; that is the entire reason pkg200 built it. No new honour surface, no parity chasing (pkg119-B/pkg180 own absolute Cycles agreement — a row that moves the pixel in the promised direction PASSES here even at the known ~3× light-energy factor).

## Confirmed root causes (verified against code 2026-08-14, not just quoted from the findings doc)

- **A** — `module/blender_module.cpp:1863` calls `cuda_wavefront_render(..., maxDepth, ...)`; the five per-type bounce args (`diffuseBounces/glossyBounces/transmissionBounces/volumeBounces/transparentBounces`) are passed to the CPU `renderer.render(...)` at L1906 but **never to the GPU call**. `cuda_wavefront_render`'s signature (`gpu_wavefront_snapshot.cu:1294`) has no per-type-bounce params at all.
- **B** — `blender_addon/__init__.py:4773` reads `world.light_settings.max_bounces`; `light_settings` is the AO datablock and has **no** `max_bounces` member, so `getattr(..., 1024)` always wins and the control is inert. The real Cycles prop is `world.cycles.max_bounces`.
- **C** — `filterGlossy` stored (`include/raytracer.h:2123`, setter :2259); **zero references in `src/gpu/`**.
- **D** — `pixelFilterType`/`pixelFilterWidth` stored (`include/raytracer.h:2132-2133`, setter :2291); **zero references in `src/gpu/`** (the wavefront does no reconstruction filtering at splat).
- **E** — `useReflectiveCaustics`/`useRefractiveCaustics` stored (`include/raytracer.h:2124-2125`, setters :2260-2261); **never read in `src/gpu/`**. GPU photon caustics gate on a *separate* `usePhotonCaustics` opt-in (pkg113); the native toggles are unwired.
- **F** — no `transparentFilm`/background-alpha handling anywhere in `src/gpu/`; the GPU alpha buffer stays opaque (background alpha 1.0).
- **use_light_tree** — `blender_addon/settings_map.py:101` maps `scene.cycles.use_light_tree` to the custom `light_sampler` tri-state (`renderer.set_light_sampler`); the exporter reads the tri-state, never the native bool. Toggling the native prop changes nothing (a semantic mismatch, not a kernel gap).

### Stage 2 — GPU plumbing, LOW register risk (host/splat/pre-pass, not the shade kernel's per-ray live state)

3. **Finding F (transparent film) — SHIPPED (F-alpha only) / F-glass RECLASSIFIED.**
   - **F-alpha (`film_transparent`, SHIPPED):** the GPU wavefront now writes per-pixel alpha honouring transparent film. A bounce-0 background-miss coverage accumulator (`c_wfMissCoverage`, published per frame like the pkg197 guide binding, atomicAdd in `intersectPathSlot`'s miss branch) counts primary-ray samples that reach the background; the driver derives `alpha = clamp(1 - miss/samples, 0, 1)` and fills `Camera::alphaBuffer` (opaque 1.0 when transparent film is off). Register-neutral for shade (rides the intersect stage), byte-identical when off (null pointer). **This is the FIRST implementation of transparent-film alpha in the engine** — the spec's "mirror the CPU path" premise was false: `getUseTransparentFilm()`/`getTransparentGlass()` and the stored flags are read *nowhere* on the CPU (`SampleResult.alpha` is a constant 1.0), so the CPU is equally inert. Recorded honestly in the results delta.
   - **F-glass (`film_transparent_glass`) — RECLASSIFIED to a follow-up feature (next-round architect).** Its predicate (`p_changes_pixels`) tests the **beauty luminance**, not alpha: honouring it requires real Cycles "transparent glass" *world-through-glass compositing* (glass shows the background, changing RGB), a genuine new feature touching the miss/shade path — not the alpha copy-back this item was scoped as. Not deliverable as a Stage-2 host-side change; filed as a follow-up candidate.
4. **Finding E (caustic toggles) — RECLASSIFIED to Stage 3 (register-hostile, probe-gated).** Verified against code 2026-08-15: the pkg113 photon pre-pass is **never enabled** in the honour scene — nothing (addon, leg, or `build_caustic`) calls `set_use_photon_caustics` or flags an `is_caustic_caster`, so `usePhotonCaustics` stays false and the pre-pass never runs. Gating an already-off pre-pass on the native toggles produces **no pixel change** → the `caustics_reflective`/`caustics_refractive` rows cannot flip on a verbatim rerun. The actual caustic signal on the floor is the **wavefront path tracer's own reflective/refractive paths**, not the photon pre-pass; honouring the toggles Cycles-style means classifying and suppressing those specular-caustic light paths in the shade/continuation logic — **per-ray path-history live state in the REG-254 shade kernel**, which is exactly Stage 3's shape (register-hostile, must clear the up-front cuobjdump probe). Cross-referenced in Stage 3 item 8 below.
5. **Finding D (pixel reconstruction filter) — `filter_width` SHIPPED (PASS); `pixel_filter_type` honoured-but-sub-threshold (HONEST-FAIL).** `pixelFilterType`/`pixelFilterWidth` are honoured on the GPU wavefront via **filter importance sampling** at primary-ray generation (`stage_init.cu::filterSample`): the sub-pixel offset is drawn from the filter's own distribution over the full `filter_width` (BOX uniform / GAUSSIAN Box-Muller / BLACKMAN-HARRIS rejection), accumulated with unit weight — the canonical Cycles/PBRT approach (NOT a cross-pixel splat; see `.astroray_plan/docs/pkg201-pixel-filter-research.md`). Width > 1 crosses pixel boundaries and blurs edges. Box ignores width and is byte-identical to the pre-pkg201 default, so the fleet baseline is untouched. Register-neutral for shade (lives in the primary-ray stage). The `filter_width` row flips HONEST-FAIL → PASS (measured GAUSSIAN 0.5 vs 4.0: grad 0.21584 vs 0.21317, ratio 1.0125). The `pixel_filter_type` row (BOX@1 vs GAUSSIAN@3) is honoured in the correct direction but lands 0.83% sharp (grad 0.21583 vs 0.21406, ratio 1.0083), below the `p_grad_sharper` 1% bar, because the shipped GAUSSIAN uses σ=width/6 (matching the CPU `filterSample`, raytracer.h:2443) which is narrower than Cycles' — so GAUSSIAN@3 barely out-blurs BOX. The Cycles-accurate width→σ mapping touches the σ shared with the CPU and is a CPU+GPU filter-parity change filed as **pkg203**; it is deliberately NOT made here. The matching CPU gap (CPU `filterSample` clamps every type to within-pixel, so it does not honour width) is folded into that same pkg203 follow-up.

**Stage 2 acceptance (measured, Blender 5.1 AND 5.2 identical to the digits):** pkg200 rows `film_transparent` (alpha 0.246 vs 1.000) and `filter_width` (grad ratio 1.0125 > 1.01) flip HONEST-FAIL → **PASS** re-running the driver verbatim. `pixel_filter_type` stays **HONEST-FAIL** (grad ratio 1.0083 < 1.01, correct direction; σ-mapping follow-up pkg203).
